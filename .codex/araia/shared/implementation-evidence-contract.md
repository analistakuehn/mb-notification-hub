# Implementation Evidence Contract

Defines the adapter-neutral contract that turns acceptance criteria into
machine-checkable implementation evidence. The contract governs PLAN and
IMPLEMENT without prescribing one universal coding ritual.

## Principle

Every acceptance criterion must name an observable outcome and the evidence
that will prove it. An implementation strategy is a means of producing that
evidence, not the evidence itself.

No agent statement such as "implemented", "looks correct", or "tests pass"
satisfies this contract. Evidence comes from a deterministic command,
an inspectable runtime observation, or an explicitly reviewed artifact.

## Evidence Contract Shape

Every Delivery Slice declares `Evidence contract version: v2` and carries an
`## Evidence Contract` table with one or more rows per acceptance criterion.
Any other version is invalid and must be regenerated by the canonical PLAN
workflow:

| Field | Required | Meaning |
|---|---|---|
| `AC` | Yes | Stable criterion identifier local to the Delivery Slice. |
| `Observable outcome` | Yes | User-, system-, or operator-visible behavior. |
| `Oracle` | Yes | Exact signal that distinguishes pass from fail. |
| `Strategy` | Yes | One strategy from the registry below, or `adaptive`. |
| `Fast check` | Yes | Cheapest focused command or observation for the inner loop. |
| `Boundary check` | Yes | Broader validation required before the Task or Delivery Slice becomes a candidate. |
| `Risk` | Yes | `low`, `medium`, `high`, or `critical`, with a short rationale for high/critical. |
| `Evidence` | Initially empty | Durable command result, artifact path, trace, screenshot, or report reference recorded during IMPLEMENT. |

Example:

```markdown
## Evidence Contract

| AC | Observable outcome | Oracle | Strategy | Fast check | Boundary check | Risk | Evidence |
|---|---|---|---|---|---|---|---|
| AC-1 | System rejects expired coupons | Result is `ExpiredCoupon` | test-first | `dotnet test --filter CouponValidatorTests` | module tests + build | medium | pending |
| AC-2 | API exposes the rejection consistently | HTTP 422 with code `COUPON_EXPIRED` | contract-first | focused API contract test | service integration suite | high: public contract | pending |
```

## Quality Obligation Overlay (v2)

Evidence Contract v2 also carries an `## Quality Obligations` table. PLAN
projects every applicable G5/G6 row from the SPECIFY Verification Plan into an
implementation owner so IMPLEMENT produces and observes quality instead of
VERIFY discovering it for the first time.

| Field | Required | Meaning |
|---|---|---|
| `Source` | Yes | Stable Verification Plan row, NFR, contract, risk, or hard-gate reference. |
| `Gate` | Yes | `G5` or `G6`. |
| `Obligation` | Yes | Observable quality property or hard gate. |
| `Applicability` | Yes | `applicable`, `not-applicable`, or `rollout-only`. |
| `Evidence owner` | Yes | Acceptance criterion, whole Delivery Slice, or `L4-spec`. |
| `Sensor / oracle` | Yes | Deterministic pass/fail command or observation. |
| `Status` | Yes | Initially `pending`; then `verified`, `not-applicable`, `rollout-only`, or `blocked`. |
| `Evidence` | Yes | Durable result or the evidence-backed disposition. |

Example:

```markdown
## Quality Obligations

| Source | Gate | Obligation | Applicability | Evidence owner | Sensor / oracle | Status | Evidence |
|---|---|---|---|---|---|---|---|
| Verification Plan: PERF-1 | G6 | P95 <= 200 ms at declared load | applicable | L4-spec | representative load test | pending | pending |
| Verification Plan: OPS-2 | G6 | Production alert observes failures | rollout-only | SLICE | homologation exercise; owner SRE; revisit before release | rollout-only | Verification Plan exclusion |
```

Test effectiveness is one of these obligations whenever the Verification Plan
declares a mutation target. `shared/test-effectiveness-sensor.md` owns its
runner, trigger, threshold source, and gate behavior; this table only carries
the row.

Every applicable obligation must have exactly one accountable evidence owner,
although one sensor may prove several rows. `not-applicable` requires evidence
from the approved Verification Plan. `rollout-only` is valid only when that
plan explicitly excludes the observation from G6 and records an owner,
environment, and revisit condition. IMPLEMENT cannot downgrade a G6 target to
`rollout-only`.

At Delivery Slice completion, the adapter writes a machine-readable sidecar at
`.araia/runs/{SPEC-ID}/IMPLEMENT/{SLICE-ID}$quality-obligations.json`. G5
aggregates those sidecars with `L4-spec` results into the assurance receipt
that `shared/implementation-assurance-contract.md` defines.

## Strategy Registry

| Strategy | Use when | Required starting evidence |
|---|---|---|
| `adaptive` | The Delivery Slice allows the IMPLEMENT loop to select from the strategies below using repository evidence and risk. | Record the strategy decision before the first source edit. |
| `strict-tdd` | A project constitution or explicit Delivery Slice decision requires the RED -> GREEN -> REFACTOR -> DOCUMENT strategy. | Failing test for every production increment. |
| `test-first` | New deterministic domain behavior benefits from test-driven API and rule design. | Focused test fails for the intended assertion. |
| `reproduce-first` | Fixing an observable defect. | Deterministic reproduction fails before the fix. |
| `characterization-first` | Changing legacy behavior that lacks a regression safety net. | Test captures the current behavior before modification. |
| `contract-first` | Changing an API, event, message, schema, or provider boundary. | Consumer/provider contract fails or an approved contract artifact is executable. |
| `scenario-first` | Changing a user journey or operator workflow. | Reproducible scenario fails in the target runtime surface. |
| `approved-scenarios` | The outcome is easiest to state as a frozen example set (rendered output, generated document, report, or complex payload) that a human approves once. | An approved scenario file exists and was confirmed against the accepted requirement; any later diff is a violation until re-approved. |
| `validation-first` | Changing infrastructure, policy, configuration, migration, or architecture enforcement. | Plan, policy, fitness, or dry-run check fails for the intended invariant. |
| `behavior-preserving` | Refactoring without intended behavior change. | Existing focused and boundary checks are green before the edit. |
| `prototype-first` | The Delivery Slice explicitly requests a bounded spike with disposable output. | Record the time/scope boundary and disposal decision. |

`prototype-first` output cannot become an integration candidate. The Task must
either discard it or convert it to another strategy and satisfy that strategy's
evidence requirements.

## Strategy Precedence

1. An explicit approved Delivery Slice strategy wins.
2. An accepted ADR, project constitution, or adapter safety rule narrows the
   allowed strategies.
3. `adaptive` selects the cheapest valid strategy that can prove the outcome.
4. High- and critical-risk work cannot use `prototype-first`.
5. When evidence supports two materially different strategies with no safe
   tie-break, stop for a technical decision; do not select by keyword.

## Evidence States

Each row moves through:

```text
pending -> producing -> observed -> boundary-verified
                    \-> blocked
```

- `observed`: the focused oracle passed, and the evidence reference captures its
  result.
- `boundary-verified`: the required broader check passed after the Task's
  changes were complete.
- `blocked`: the oracle is unavailable, ambiguous, flaky beyond the retry
  budget, or contradicts a higher-precedence artifact.

A Task is complete only when all rows it owns are `boundary-verified`. A
Delivery Slice is a candidate only when every acceptance criterion is
`boundary-verified`, every applicable quality obligation it owns is `verified`,
every disposition is evidence-backed, and no required risk evaluation remains
open.

## Evidence Quality Rules

1. Prefer outcomes over implementation details.
2. Prefer deterministic graders over model judgment when both can assess the
   same property.
3. A builder-generated test qualifies as focused-behavior evidence, but
   high-risk work also requires an independent or black-box boundary check.
4. A passing test that never demonstrated the intended failure is insufficient
   for `strict-tdd`, `test-first`, `reproduce-first`, or `contract-first`.
5. An oracle that cannot fail is not evidence. Apply
   `shared/test-tautology-rules.md` before promoting any row to `observed`, and
   record the falsification answer for high- and critical-risk rows. Test order
   never substitutes for this check.
6. Regression value is measured, not inferred from the strategy that wrote the
   tests. Apply `shared/test-effectiveness-sensor.md` wherever the Verification
   Plan declares a target.
7. Flaky results are evidence of an unhealthy oracle, not permission to ignore
   it.
8. Store concise evidence references; do not paste unbounded logs into the Delivery Slice
   or progress state.
9. Source and test identifiers must describe behavior, never coded SPEC/Delivery Slice/AC
   identifiers, per `shared/no-spec-refs-in-implementation.md`.

## Adapter Responsibilities

Each adapter must declare:

- how it maps Delivery Slice acceptance criteria to this table;
- commands available for focused, Task-boundary, and SLICE-boundary validation;
- strategy restrictions for its runtime and risk domains;
- signals that require an independent evaluator;
- how workers return evidence references without mutating the manifest.

The Araia orchestrator owns manifest state. Implementation skills and workers
produce evidence and candidate metadata but never mark a Delivery Slice completed.

## Contract Versions

A Delivery Slice without `## Evidence Contract` is invalid and halts before
IMPLEMENT. Regenerate it through the canonical PLAN workflow; do not infer
oracles or acceptance boundaries from prose.

`shared/risk-based-implementation-evaluation.md` requires independent
implementation evaluation only when the declared risk or observed loop state
activates a trigger. The evaluation supplements and never replaces
deterministic validation sensors.
